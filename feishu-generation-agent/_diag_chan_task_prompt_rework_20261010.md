## 二、三个根因（互相独立，都会造成「改了没用」）

### 根因 1：大部分「重跑」根本没改提示词

#6/#7、#8/#9 是逐字相同的重摇；其余相邻两次相似度也在 0.975~0.999。
用户以为在「调提示词」，实际在重摇同一版。每次重摇都要真花钱出一次 10 秒 seedance2.5 视频。

### 根因 2：整篇「重新生成计划」会把累积的返工要求清零（#5、#11）

#5 `1c65c6e4` 与 #11 `e3ac684b` 的事件流与其它 run 完全不同 —— 它们从
`ingest_source → normalize_document → analyze_images → plan_requirements → audit_plan → validate_plan`
重跑，**没有 `clone_approved_plan`**，即「整篇重做计划」。
重做后新任务的 `rework_requirements` 变成 **空列表**，之前累积的要求不再参与提示词。

对照时间线（#10 → #11 → #13）：

```
13:04  #10 f0cbf83a  rework=[…, "蜡是比较硬化状态的"]        ← 用户明确要求硬化
13:36  #11 e3ac684b  整篇重做计划 → rework=[]                 ← 硬化要求被丢掉
14:37  #13 fffc5d0a  rework=["蜡的质感是明显硬化的，严格遵循参考视频"]  ← 用户又得说一遍
15:09  #15 cf40359d  rework=[…, "上一版质感对了，但是这一版质感又变回去了…"]
```

用户那句「上一版质感对了，但是这一版质感又变回去了」，在这条时间线上是可解释的：
**对的版本来自一份后来被整篇重做丢掉的提示词。**

### 根因 3：两条最硬的验收条件，本来就不是文本能稳控的

1. **「铲子必须铲最右侧的红色条状蜡，不要铲橙色」**
   参考图是以 `role=reference_image`（**软参考**）提交的（`reference_mode=multi_reference`），
   不是首帧。模型每次都会**重新铺一遍彩虹条带**，条带位置没有像素锚点 →
   「最右侧」这句话在成片里没有可对齐的对象。
   实测（抽帧看画面，用本地视觉模型核对）：
   - #14 ca83b32b t=5s：铲子在**红色**蜡上 ← 用户认可的那版
   - #15 cf40359d t=5s：铲子在**橙色**蜡上 ← 用户投诉的那版
   两版**提示词视觉段逐字相同**，所以这不是「词没写对」，是摇。

2. **「蜡的质感是明显硬化的」**
   这是材质观感，在 1400+ 字的提示词里只占一个从句；而本轮 #15 的融合结果
   把这句要求落到了 **【全局声音与字幕约束】** 里（加了「脆性断裂」四个字），
   **视觉段一个字没动**。融合器的合格判据只拦「与原文一致 = 没改」和
   「从画面描述里抄物件当新约束」，**不拦「改错段落」**，所以这次错落点被放行了。

## 三、建议的四个动作（按性价比排序）

| | 动作 | 性质 | 收益 | 代价/风险 |
|---|---|---|---|---|
| A | **空返工要求不许重跑**（提示词与上一版逐字相同时，UI 上给明确提示） | 前端/校验小改 | 立刻止住「花钱重摇」 | 低 |
| B | **整篇重做计划时继承 `rework_requirements`**（把历史要求带进新计划，而不是清零） | 后端逻辑 | 直接消灭「又变回去」这一整类投诉 | 需重启 8765；要定「哪些要求该继承」的口径 |
| C | **把「铲哪条颜色」改成首帧锁定**：把参考图（或先裁出右侧红条区域后的图）以 `role=first_frame` 提交 | 生成语义变更 | 颜色位置逐像素锁死，这是唯一能真正稳住验收条件的做法 | 与文档里「尽量不用首尾帧、用提示词控制动作」的团队口径冲突；方舟硬约束：有首帧时不能再指定 ratio（代码已有 `_apply_frame_ratio_constraint` 处理） |
| D | **融合落点校验**：要求里的视觉/材质词必须出现在视觉段（【全局视觉设定】/【详细情节】）才算落实，只落在声音段 → 判不合格重试；并给「不得接触橙色条纹」补进 `must_avoid` | 后端逻辑 | 让「改提示词」这件事真的作用到画面上 | 需重启 8765；融合多一次重试 |

### 行为变化

1. **整篇「重新生成计划」不再丢历史**：新 run 从同一条需求历次运行的检查点里收集累积的
   `rework_requirements`（最多 20 条历史运行、最多 12 条要求），喂进规划上下文，并并回新任务。
   全新需求不受影响（无历史 → 空）。
2. **视觉/材质类要求若只落在【…声音…】段，融合结果判不合格**：重试最多 4 次（每次带上
   不合格原因）；仍失败则正文**原样保留**，事件如实说「没有改变提示词正文」。
3. 事件可核对：`plan_requirements` 会写「已从这条需求的历史运行继承 N 条返工要求」。

### 还没解决的（要稳定就必须做）

**根因 3 仍在**：参考图以 `role=reference_image`（软参考）提交，模型每次重铺彩虹条带，
「铲最右侧红色」没有像素锚点 —— 同一份提示词既出过红色也出过橙色。**B+D 让「改提示词」
真的作用到画面上、且历史不再丢，但改不动这个随机性。**

要「稳定复现」，只剩首帧（方案 C）：把参考图（或先裁出右侧红条区域的图）以
`role=first_frame` 提交，让条带位置逐像素锁死。两个已知冲突需要先定口径：
① 与文档「尽量不首尾帧、用提示词控制动作」的团队口径冲突；
② 首帧会锁住构图，与「蜡条竖直长度缩短为参考图一半」冲突（需先在图上裁切）。
