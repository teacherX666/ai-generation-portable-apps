# MiniMax H3 JSON 导演 · 精简版

> **一句话定位**：把每个 H3 镜头规划成一个**可编辑的 `h3-director-json-v1` JSON 对象**，在保留官方 T2VA / I2VA / FL2VA / L2VA / Ref2VA 语义的前提下，让提示词结构化、可校验、可批量改。
>
> ⚠️ **重要边界**：JSON 是**喂给 H3 的提示词文本**，不是 H3 API 请求体，也不是 MiniMax 官方 schema。JSON 层**绝不能改变**官方的模式含义、参考标签、任务类型、保留关系、台词标签、说话人编号或声音/音乐分离。
>
> 本文件为**免费分享的精简版**（约完整版 1/4）。完整版（会员）含：JSON Schema 全文、`base-en.txt` / `ref-en.txt` 官方指南、`enhancement-rules.md` 增强规则。

---

## 一、语义决策优先级（冲突时按此顺序）

1. 用户当前明确的要求
2. **实际可检查的媒体中可见的事实**
3. 所选模式的官方 H3 指南
4. JSON Director 规划指引
5. JSON Director 默认值

机器可读的 JSON Schema **独立管辖输出结构**。若某个请求无法在不违反 Schema 的前提下表达，**说明冲突，而不是编造字段或枚举值**。

⚠️ 官方指南描述的是**语义意图，不是 JSON 输出模板**。序列化时忽略其旧版纯文本段落布局和示例字数目标，把底层含义映射到当前 JSON Schema。

## 二、七步构建流程

### 1. 检查并规范化请求
确定：目标时长与宽高比 → 可用的文本/图/视频/音频 → 每个素材的主要职责 → 精确台词、歌词、可见文字、请求的变更、须保留事实、明确排除项 → 结果是单个 4–15 秒片段还是更长序列。

**检查可用媒体。不要从文件名推断未见内容。** 只有当答案会改变 H3 模式、素材映射或预期结果时才提一个关键问题，否则做最小合理假设继续。

> **图片资产台账**：按**实际上传顺序**维护私有台账，记录每张图可见内容、主要职责、支持哪些语义主体或具体帧锚点。第一张上传的是 `<Picture 1>`，第二张 `<Picture 2>`，**不按重要性或首次使用顺序重编号**。

### 2. 时长路由闸门（选镜头/参考/节奏之前必过）
- 总时长在 **4–15 秒（含）** → 创建**恰好一个** H3 片段和**恰好一个**最终 JSON 对象，`format.duration_seconds` 等于该总时长
- **绝不因为**"多张图、多个主体、多镜头、快切、节拍同步、密集分镜、复杂 Ref2VA 关系"就拆分 4–15 秒请求 —— 这些都应表示为单个 JSON 内 `storyboard` 的多个条目
- **镜头是单个生成片段内部的摄影/剪辑区间，不是独立生成的 H3 片段。** 10 秒请求里有 6 个镜头，仍然产出**一个** 10 秒 JSON 对象
- **只有总时长超过 15 秒才拆分**。用户要多个独立的 4–15 秒视频时，各自作为独立请求处理
- 4–15 秒请求显得过载时，**保持一个片段**并警告或询问是否简化内部分镜。不要用"偷偷多开几次生成"解决密度问题

### 3. 先分解"锁定了什么"，再选模式
不要把图片/视频/音频当作一条不可分割的参考指令。先拆成独立的**职责轴**，对每条轴判定：**anchored（锚定）/ preserved（保留）/ guided（引导）/ free（自由）**：

| 轴 | 含义 |
|---|---|
| `identity` | 角色、产品、物体、服装等可复用的可见身份 |
| `environment` | 应保持可识别的世界或场景 |
| `composition` | 精确的空间排布、构图、布局、姿态或端点画面几何 |
| `motion` | 动作路径、镜头行为、剪辑节奏或时间结构 |
| `appearance` | 光线语言、色调、质感、图形处理或风格 |
| `audio` | 复制的信号、人声、音乐、节奏、环境或声音特征 |

- **anchored** — 具体帧、时间点、源视频或音频信号必须用在特定结构位置
- **preserved** — 语义身份或世界必须可识别，但新姿态、构图、局部细节可以生成
- **guided** — 源影响结果，但不是硬性连续义务
- **free** — H3 可在用户简报内自由发挥

> **关键判断**：一张高完成度的图可能同时含身份、环境、构图、字体、姿态、光线和风格。**不要自动全部保留** —— 只编码用户真正需要的职责，否则强参考会把每个镜头都拽回同一个姿态或构图。

**环境身份 ≠ 构图身份**。保留环境 = 保持同一语义世界、地点族、氛围和必要的稳定空间事实，**不要求**相同机位、主体位置、道具布局或精确的源构图。

### 4. 每个 JSON 对象选且仅选一个官方模式

从**结构锚定**判断，不只是"有没有上传图片"：

| 模式 | 何时用 |
|---|---|
| `T2VA` | 纯文字生成，无素材参考 |
| `I2VA` | 用户希望**一张**提供的图成为**字面意义的开场帧**，或希望生成动作从该可见帧直接延续。用恰好一个 `<Picture 1>` 在 `0.0` 秒 |
| `FL2VA` | 用户希望提供的图成为**字面意义的开场帧和结束帧**。`<Picture 1>` 在 `0.0`，`<Picture 2>` 在总时长处 |
| `L2VA` | 用户希望**一张**图成为**字面意义的结束帧** |
| `Ref2VA` | 素材被语义化或时间化使用，不要求是字面端点；或任务涉及身份、环境、风格、姿态、动作、镜头、节奏、分镜、关键帧、源视频编辑/延续、音频参考 |

> **上传了图片 ≠ I2VA。** 想保留图中内容但允许新开场构图 → **Ref2VA**。说"让这张图动起来""从它继续""把它作为第 0 帧" → 用对应端点模式。
>
> 端点锚与额外独立参考同时需要时 → 用 **Ref2VA**，通过 `<Picture N>` 保留具体端点，其余职责单独映射。
>
> **宽高比、分辨率、界面侧运行时设置不决定语义模式。**

### 5. 按职责映射参考（只用官方标签）

| 标签 | 用途 |
|---|---|
| `<Picture N>` | 具体帧、关键帧、构图锚、分镜锚 |
| `<Subject N>` | 从源素材抽象出的可复用语义职责：角色、产品、物体/道具、环境、服装、风格、动作、姿态 |
| `<Video N>` | 实际源视频、延续源、时间/镜头/剪辑/节奏参考 |
| `<Audio N>` | 被复制或参考的实际音频信号 |

- 用 `character_identity` / `product_identity` / `object_identity` / `wardrobe_identity` / `environment_identity` 保留**"是什么"**，而不自动保留源姿态或布局
- 只用 `composition_reference` 表示源排布/构图/布局要影响新镜头
- 用 `pose_reference` / `action_reference` 表示姿态或动作本身是可迁移职责
- **不要发明非 Schema 角色**（如 `prop_identity` —— 用 `object_identity`）

> **最小职责集原则**：一个物理素材提供多个职责时，只分离真正需要的。不要默认从同一张高完成度图同时造出 `style_reference` + `environment_identity` + `composition_reference` —— 这个组合会过度绑定生成。

**编号规则**：每个标签族**各自从 1 连续编号，无空档**。每个参考只有一个主要 `role`。`<Subject N>` 在 `sources` 里列出原始素材标签，**不要**为只提供该主体的素材再创建冗余的独立 Picture/Video 条目。

**relationship 只在 Ref2VA 且需要明确保留或迁移时使用**：
- 具体开场/结束/关键帧 → `fully_preserved` / `partially_preserved`
- 构图/分镜/结构性镜头剪辑节奏参考 → 可用 `weak_reference`
- 动作/主体迁移 → `attribute_transfer`
- 音频复用 → `fully_copy` / `partially_copy`；非复制音频引导 → `reference` / `weak_reference`

**每个 `keyframe` 是具体的时间局部锚**：`scope: "shot_specific"`，恰好一个目标镜头，`at_seconds` 落在该镜头内。

### 6. 撰写导演 JSON
只用 Schema 允许的顶层模块。核心骨架：

```json
{
  "schema": "h3-director-json-v1",
  "format": { "duration_seconds": 10, "aspect_ratio": "16:9" },
  "mode": "Ref2VA",
  "references": [ ... ],
  "storyboard": [ ... ],
  "direction": { "visual_style": "..." },
  "sound": { ... }
}
```

### 7. 超过 15 秒的请求
拆成多个 4–15 秒的 JSON 对象，每个是独立生成调用。跨片段连续性通过共享的 `<Subject N>` 定义、一致的风格描述与延续锚实现。

## 三、交付前校验

- [ ] JSON 是合法 UTF-8 且通过 Schema 校验？
- [ ] 4–15 秒请求只产出**一个** JSON 对象？
- [ ] 模式由**结构锚定**决定，而非"有没有图"？
- [ ] 每个参考只有一个主要 role，职责集是**最小的**？
- [ ] 标签族各自从 1 连续编号，无空档？
- [ ] `<Picture N>` 按**实际上传顺序**编号，未被重排？
- [ ] 环境身份与构图身份分开处理？
- [ ] relationship 只在 Ref2VA 且必要时使用，且与 role 匹配？
- [ ] keyframe 都是 `shot_specific` + 单目标镜头 + `at_seconds` 在镜头内？
- [ ] 官方语义（模式含义/标签/台词/说话人编号/声音音乐分离）**未被 JSON 层改写**？

## 四、边界

- 不把 JSON 当作 H3 API 请求体
- 不发明 Schema 之外的字段或枚举值
- 不覆盖官方模式语义
- 不声称这是 MiniMax 官方 schema
